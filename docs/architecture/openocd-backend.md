# Opt-in CMSIS-DAP/OpenOCD backend

`tools/nrfkit openocd` reuses the existing image manifest loader, ELF/HEX address
checks, immutable programming snapshots, probe locks, process timeouts and run
reports. The normal nrfutil/J-Link commands remain the reference backend. An image
manifest's existing nrfutil contract is preserved; selecting this separate CLI
explicitly chooses the evaluated OpenOCD transport and records its executable and
Tcl hashes in the run report.

Supply an external OpenOCD build with the `nrf54lm20` application-RRAM driver and
matching `target/nordic/nrf54lm20.cfg` scripts. The SDK neither builds a fork nor
adds it to the consumer dependency graph. Local paths belong only in the inventory.
The evaluated external baseline is OpenOCD
`046c040cb0012e2f908bb11009b39bf502cff6f3` with application-RRAM and checked system-reset patches.
This is not a claim of upstream OpenOCD flash support.

The adapter setup is generated by the repository. It selects exactly one discovered
CMSIS-DAP USB bulk interface and serial, binds GDB to loopback only when required,
and disables Tcl/Telnet services. The target script owns reset policy through
`nrf54lm20_reset_config system|pin`; an older script without this contract is
rejected before adapter initialization. The default system reset checks LM20 PART,
halts the core, requests POWER constant latency and waits for readiness before
AIRCR.SYSRESETREQ (LM20 anomaly 63). This preserves debug state for vector catch.
The core stays halted during preparation so firmware cannot release CONSTLAT.
Normal reset/run uses reset/halt followed by resume for the same reason.

Physical recovery is explicit via `reset --pin` and requires nRESET wired to SRST.
It uses `srst_gates_jtag` and releases SRST before reconnecting. PinReset resets
debug components, so it cannot guarantee a halt at the reset vector and cannot be
combined with `--halt`. Connect-under-reset is not supported by this setup.
Supported SWD requests are 1000, 2000 and 4000 kHz, with the conservative request
as default; these are requests, not measured SWCLK frequencies.

Before memory operations act on the target, FICR PART must identify LM20A or LM20B and report
2036 KiB RRAM. PART, VARIANT and device ID offsets come from the locked A/B Datasheet
v1.0 §4.2.4.1. Receipts retain the actual identity. The DK's LM20B validates shared
LM20 functionality; NPU support is outside scope.

- `list` enumerates the adapter without connecting to the target.
- `info` reads target identity; it can enter debug-interface mode.
- `flash --manifest` programs guarded addressed HEX snapshots without erase and
  verifies them. The CPU remains halted. No arbitrary BIN address is accepted.
- `clear-rram` is an explicitly destructive maintenance command requiring user
  authorization to discard all ordinary application RRAM, including boot code,
  settings and scratch data. It double-reads and saves the complete bank before
  writing an addressed, range-checked FF snapshot over `0x00000000..0x001fcfff`.
  A separate `backup.json` is saved before writing; full readback must match FF.
  The CPU stays halted. This does not use CTRL-AP ERASEALL or touch configuration
  memory, and it cannot bypass inaccessible or protected application memory.
  Restoring its full-bank backup requires a separately reviewed manifest whose
  ordinary RRAM allowlist covers that complete range; an image-only manifest is
  insufficient. A failed clear keeps its backup but does not imply rollback.
- `backup --manifest` accepts repeated manifests and saves the union of bytes those
  images can overwrite, rounded to 16-byte RRAM units within each allowlist. Two
  independent reads must match before addressed HEX backups are published.
- `restore --manifest --backup-report` requires a successful backup, unchanged
  artifact hashes, matching target identity, and ranges within the supplied
  manifest's allowlist. It verifies restored bytes and leaves the CPU halted.
- `backup` and `restore` accept `--include-settings` to preserve the separate,
  16-byte-aligned ordinary RRAM settings span declared by the audited ELF. The
  default remains image bytes only; protected regions are never included.
- `reset` performs the checked system reset, then resumes firmware. `--halt`
  instead leaves the CPU at the reset vector. Both require application debug
  access; a failed identity, halt or CONSTLAT readiness check aborts before the
  reset request. `--diagnostics` saves detailed OpenOCD reset tracing.
  `--pin` attempts physical recovery before reading identity and releases the
  line even when the reset sequence reports an error. Select the intended probe
  before using it. Success requires a subsequent LM20 identity check; failure
  does not establish target state. Programming and restoration validate identity
  before any memory write.
- `gdb-smoke --manifest --gdb` exercises main and single-step with hardware
  breakpoints. `--runtime-contract` adds the hardware-validation firmware's RAM,
  post-main, reset-vector and watchpoint checks. GDB's register cache is flushed
  after monitor resets before reading PC or continuing. `--attach --observe SYMBOL` inspects
  an existing image without reset, then resumes and detaches. It does not prove
  that the supplied ELF matches running firmware; establish that separately.

Ordinary snapshots and backups are not authorization to touch configuration,
protection, factory or one-time regions. Restoring application bytes does not restore
volatile peripheral state; choose an explicit reset/cold-start phase afterward.
GDB failure leaves target state unclaimed, with server cleanup recorded. Software
flash breakpoints, power-loss programming recovery and full M2/M7 acceptance are
separate evidence, not inferred from a successful attach.

Host tests cover argument quoting, identity/range rejection, rounded backup bounds,
clear failure paths, reset ordering, and stale or wrong-target restoration.
Guarded programming/readback and double-read backup/restore have passed on LM20B.
With nRESET connected to adapter SRST, physical reset/run and GDB attach/read have
passed: the validation firmware reached its main loop with the expected marker,
RESETPIN set, and zero CFSR/HFSR. The same observations passed after a hub power
cycle of the target and probe. Hub power commands are not voltage measurements.
On 2026-10-03, the checked system reset and complete runtime contract passed at
1000, 2000 and 4000 kHz requests: Reset_Handler, main, single-step, post-main state,
RAM write/read and a hardware watchpoint on startup's RAM clear. Default reset/run
and explicit pin reset also passed; the firmware was resumed after validation.
This validates LM20B/AABD with CherryDAP USB bulk firmware 2.1.1, an LLVM 24
RelWithDebInfo hardware-validation image and Arm GDB 16.3.90. LM20A remains covered
by source review and host tests, not by this board run. Historical power measurements
are recorded separately in the [measurement results](../validation/power-measurement-2026-09-11.md).

If running firmware locks application writes until reset, a restore can fail
without an image-guard failure. Where a separately backed-up writable boot region
is available, program the quiet probe there, cold-start it, restore application
and settings, then restore the original boot region while halted. Do not modify
protection settings or infer that an ineffective pin reset cleared runtime locks.
